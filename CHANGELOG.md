- **RBAC service (runtime role/permission management)**: Runtime-manageable roles and user-role assignments with wildcard permission checks — complements the static auth config (hardcoded admin/user/readonly in `extensions/auth.py`) with a dynamic RBAC store. New `core/rbac.py` with `RbacProvider` Protocol, `InMemoryRbacProvider` (default; thread-safe, seeds the three system roles aligned with `DEFAULT_ROLE_PERMISSIONS`), `NullRbacProvider` (disabled — deny all), `RbacManager` facade (create/get/list/update/delete roles, assign/revoke user roles, get_user_roles/get_user_permissions, check_permission, get_stats), `RoleDefinition` (name, permissions, description, is_system, timestamps), `RbacStats`, `RbacRegistry` + `@register_rbac_provider` decorator. Permission format `resource:action` with wildcards (`*` full access / `agents:*` all actions on a resource / `*:read` an action on all resources); legacy coarse permissions (`read`/`write`/`invoke`/`delete`/`admin`) normalize to `*:<action>` for compatibility. System roles are delete-protected; deleting a custom role cleans up its assignments. Deny-by-default: unknown user, no roles, empty resource/action, or disabled service → False. Limits: 500 roles, 100 permissions/role, 20 roles/user, role name ≤ 64 (lowercase alnum/hyphen/underscore). 11 new API endpoints: `GET/POST /rbac/roles`, `GET /rbac/roles/stats`, `GET/PATCH/DELETE /rbac/roles/{name}`, `GET /rbac/roles/{name}/users`, `POST/DELETE /rbac/users/{username}/roles/{role_name}`, `GET /rbac/users/{username}/roles` (roles + effective permission union), `POST /rbac/check`. 2 new read-only agent tools: `rbac_check_permission`, `rbac_list_roles` (grant/revoke are admin API operations; `default_enabled=false`). New `RbacConfig` in schema (`rbac.enabled` + `rbac.provider` + `rbac.seed_system_roles` + `rbac.options`). New error codes `AGENTBASE_RBAC_001`/`002`/`003`/`004`. ### Fixed
- **`SystemConfigConfig` missing `options` field (AttributeError on real factory/manager construction)**: Same class of bug as the earlier `CalendarConfig` fix — `SystemConfigConfig` was introduced without an `options` field while `api.py::_get_system_config_manager()` and `AgentFactory.system_config_manager` both pass `**cfg.options`. Hidden until now because system-config API tests monkeypatch the manager, and `AgentFactory.build()` tests never exercised the manager properties; adding `rbac_manager` to the factory context finally triggered the real construction path. Fixed by adding `options: dict[str, Any] = Field(default_factory=dict)`, and verified programmatically that every config class referenced via `**cfg.options` in `api.py` and `agent_factory.py` now declares `options` (all pass).
- **`CalendarConfig` missing `options` field (AttributeError on first calendar API call)**: `api.py::_get_calendar_manager()` and `AgentFactory.calendar_manager` both passed `**cfg.options`, but `CalendarConfig` never declared an `options` field — so the very first request to any `/calendar/*` endpoint with `calendar.enabled=true` raised `AttributeError: 'CalendarConfig' object has no attribute 'options'`. Not caught earlier because API tests monkeypatch the manager and bypass the real construction path. Fixed by adding `options: dict[str, Any] = Field(default_factory=dict)` to `CalendarConfig`, matching the convention of every other service config.
- **`code_execute` tool could never be assembled**: the tool function was registered directly via `@register_tool` instead of a builder function, violating the tool-factory contract (`builder(context)`). Assembly raised `TypeError` twice and the tool was silently skipped (`skip_on_error=True`). Fixed by registering `build_code_execute_tool()` which wraps the sandbox function in a LangChain `@tool`, following the same pattern as all other 36 tools. Added `tests/unit/test_tool_code_execute.py` (8 tests: factory assembly, real subprocess execution, timeout/size limits, error paths).
- **JWT hardcoded default secret (P0 security)**: `AuthConfig.secret` and `JWTAuth.__init__` both defaulted to `"agentbase-default-secret"` — anyone knowing this value could forge JWT tokens when `auth.type: jwt` was configured without an explicit secret. Fixed by: (1) defaulting `secret` to empty string in both `AuthConfig` and `JWTAuth`; (2) `_get_jwt_auth()` now raises `ConfigError` (`AGENTBASE_CONFIG_002`) on empty secret when `type=jwt` (fail-fast); (3) `JWTAuth` generates a random ephemeral secret as last-resort fail-safe (with warning log); (4) `docker-compose.yml` removed the insecure fallback. Added `tests/unit/test_jwt_security.py` (11 tests).
- **API key timing side-channel (P1 security)**: `_verify_api_key()` and `_verify_auth()` used Python `==` for API key comparison, which short-circuits on the first differing byte — enabling timing attacks to recover the key byte-by-byte. Fixed by replacing all 3 comparison sites with `hmac.compare_digest()` (constant-time comparison). Added 6 direct unit tests in `test_api_security.py::TestApiKeyConstantTime`.
- **CORS wildcard + credentials (P1 security)**: `CORSMiddleware` was hardcoded with `allow_credentials=True` while defaulting to `allow_origins=["*"]` — a combination forbidden by the CORS spec that causes browsers to reflect arbitrary Origin headers, effectively disabling CORS protection. Fixed by: (1) `allow_credentials` is now dynamically `False` when origins contain `*`; (2) `CORSConfig.allow_credentials` default changed from `True` to `False`; (3) added `effective_credentials()` method to schema. Added 6 tests (2 HTTP-level + 4 schema unit).
- **Stream semaphore bypass (P1 concurrency)**: `AgentRunner.stream()` held the `threading.Semaphore` only around `agent.stream()` (iterator creation) and released it before iterating — meaning `max_concurrency` was effectively bypassed for all streaming requests. Fixed by moving the semaphore to `acquire()` before iteration and `release()` in a `finally` block, so it covers the entire stream consumption. Added 2 concurrency tests (threading-based blocking verification + error-release verification).
- **OAuth2 test flakiness in full suite**: `test_api_oauth2.py::TestCallbackEndpoint::test_no_access_token_in_response` and `test_github_callback_flow` failed intermittently when running the full test suite (1871 tests). Root cause: the global `_rate_limiter` singleton in `api.py` was not reset between test modules — earlier tests accumulated requests in the rate limiter's sliding-window buckets, causing OAuth2 test requests to be rejected with `429 Too Many Requests` instead of the expected `502` or `302`. Fixed by adding `_reset_rate_limiter()` calls to the setup and teardown of both `client_oauth2_disabled` and `client_oauth2_enabled` fixtures, matching the pattern already used in `test_api_security.py`.
- **Stream token usage extraction (P2 bug)**: `AgentRunner.stream()` called `extract_usage_from_result(final_text)` where `final_text` is a plain string — but `extract_usage_from_result` expects a result object with `messages` attribute (LangGraph standard) or a dict with `messages` key. This meant token usage was **always 0** in stream mode, even when the model returned `usage_metadata`. Fixed by capturing the last raw event payload from `MESSAGE_FINAL`/`MESSAGE_DELTA` events during stream iteration, and passing that to `extract_usage_from_result()` instead of the plain text string.
- **Docker Compose missing env vars for optional services**: `docker-compose.yml` only passed through environment variables for base services (model keys, auth, rate limiting, PostgreSQL, Redis, metrics). All 15 optional services (audit, experiment, redaction, secrets, model_manager, prompt_manager, user_manager, apikey_manager, oauth2, usage, webhook, feedback, notification, conversation, migration) were missing from the `api` service's `environment` section — meaning Docker deployments couldn't enable these services via `.env` without modifying `docker-compose.yml` directly. Fixed by adding env var passthrough for all 15 services with sensible defaults (all `false` except `migration=true`), matching `.env.example` and `configs/default.yaml` defaults.
