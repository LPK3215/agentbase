## 摩擦（技能包改进线索）

1. **章体积**  
   02 / 07 / 10 单章很长。中度仍几乎要扫完整第 2 章全部 2.1–2.13 和第 7 章全部 7.1–7.6。对脚手架「机制存在即可」仍然要逐点写证据，一次中度 ≈ 半天级读码 + 写报告。

2. **检查点过密**  
   2.x.x 子点在脚手架上大量「有模块默认关」。表格行数高、重复「警示 / 默认关」。可考虑脚手架速查表：每节一行 + 三级口径，而不是应用型全量子点。

3. **附录 B 引用是对的，但套用时要对齐已有实现**  
   agentbase 已有 `interrupt_on` 和 `docs/extensions.md`，不是零钩子。B.2 伪码是 `beforeToolExecute`，与本仓 API 不同名。检查者必须翻译「等价接入位置」，技能正文对此只有一句「语言无关」，实操仍要判断「已有 demo 算不算二级」——本次判了算。建议 B 模板加一句：**项目已有同构机制+示例即可升二级，不必改名抄伪码。**

4. **技能仓嵌套副本**  
   技能目录下存在 `测试项目临时用/agentbase`（含 `.venv`，上万文件）。Glob/Grep 易扫错对象。应在 SKILL.md 写死：**被检根目录以用户指定为准，忽略技能仓内测试副本。**

5. **7.5.1「无清单」vs「红线触顶」**  
   10.1.2 把「红线被平均掩盖（7.5.1）」放进 block 列表。实操必须拆成：无表 = 不达标封顶原型；有表但加权稀释 = block。本次手工拆了。建议 10.1.2 正文加半句，避免检查者直接 block 无 SECURITY.md 的脚手架。

6. **默发 Agent 自主度 vs 脚手架 G 档**  
   定档对象是脚手架（G1）还是默发 Agent（G3 无闸）？技能对脚手架型写了子类，但 1.6 仍按「系统会不会自己干活」提问。实操需要双行声明（本体 G1 / 默发画像 G3）。建议 1.6 加脚手架提示：先档框架，再单独标注 default profile。

7. **工作区 vs HEAD**  
   本轮 eval 在未提交改动里。技能未要求声明「验的是工作区还是 commit」。不声明会让复评对不齐。本次写进了 01。建议定档第 8 项加「验收快照：工作区 / 指定 commit」。

8. **轻度对脚手架几乎不够**  
   自动扫描若只因「有很多模块」就跳轻度，合理；但中度工作量接近「半个重度减评测」。可考虑「脚手架中度精简包」：2 章只查接线与三级口径，7 章只查 7.5.1 + 鉴权 fail-open + 默发工具闸。
